From chain of trust to chain of time

Physical AI runs non-deterministic workloads on the same silicon as real-time control. We have learned to build a verifiable chain of trust from manufacture to runtime. The equivalent chain for time, covering how long each step may take and how much of a shared resource it may use, barely exists. This paper sets out where it breaks and what would close it.

1. The problem: no contract about interference

A robot or vehicle that runs learned perception beside safety-relevant control on one system-on-chip is running two workloads with incompatible characteristics. Inference is bursty, memory-hungry and best-effort. Control is small, periodic and has a hard deadline. They contend for last-level cache, memory bandwidth, the interconnect, interrupt delivery, the hypervisor's scheduler and, increasingly, the accelerator itself.

As the mixed-criticality primer puts it, the failure is not that the model is inaccurate. It is that the platform underneath both workloads has no contract about interference.

That sentence understates the problem in one respect. A sensor-to-actuator path does not cross one boundary. It crosses many: a field network, a device-virtualisation backend, a hypervisor, a shared memory hierarchy, a middleware layer, an executor, an accelerator queue, and back out again. A principle that holds across firmware, protocols and IPC applies to each of them: at every domain boundary, make the contract explicit, formal and machine-readable. Most of the boundaries on that path have no timing contract at all.

2. Three contracts, one pattern

Every boundary on a shared platform needs an answer along three dimensions.

DimensionThe questionMature mechanismsState
AccessWho is allowed to touch what, and what happens when they shouldn't?SMMU stage 2, TZASC, MPC/PPC, vendor equivalentsMature; the remaining errors are mostly configuration
TrustIs this component what it claims to be, running what it claims to run?DICE, SPDM, PCIe/CXL IDE, TDISPIn production in data centres; uneven elsewhere (section 6)
TimeHow long may this step take, and how much of a shared resource may it use?TSN at the network edge; LET inside some ECUsIslands only; no end-to-end chain

The access row is the subject of Security and Safety by Isolation, which reduces every hardware protection mechanism to one form: initiator identity × target resource → access policy. The same article treats MPAM as the temporal half of freedom from interference, using the same form with a partition ID, cache ways or DRAM bandwidth, and a cap. The trust row is the subject of From specification to silicon. This paper is about the third row.

The three dimensions share three requirements. Each contract must be enforced at the target, because an initiator cannot be trusted to police itself. Each must be locked before untrusted software runs, because a configuration that untrusted code can change is a convention, not a guarantee. And each must be evidenced by something other than the system being judged.

They also map onto the three questions that safety and security share. Is the system intact? is a trust question. Is it behaving as intended? is an access and time question. Can it recover to a safe, secure state when it isn't? is what each contract's miss handler is for.

3. The chain of trust as a template

The trust chain is worth studying not because timing is a security problem, but because it is the best worked example of how an industry turned an implicit assumption into a verifiable property. It has five steps, and two composition rules.

The steps run from manufacture to runtime: a hardware-rooted identity provisioned once; measured boot, which records what actually started; attestation, in which a relying party checks identity and measurements before admitting the device; runtime enforcement, in which IDE protects every transaction afterwards; and, still open, continuity, re-checking during a workload's lifetime rather than only at admission.

The composition rules matter more than the steps. First, admission and enforcement are only meaningful together: IDE without SPDM attestation is encryption without verified identity. Second, the chain is bounded by its weakest link: a platform's security posture is bounded by its least-attested component.

Proposal: build the chain of time with the same structure.

StepChain of trust (exists)Chain of time (proposed)
IdentityDICE identity provisioned at manufactureA declared timing contract per workload and per hop: demand envelope, burst profile, worst-case latency
Measured bootEach firmware stage measured as it startsThe partitioning configuration that bounds interference (cache and bandwidth partitions, SMMU stage 2, network gate schedules, core pinning) locked, then measured
AdmissionSPDM attestation before a device is trustedA critical workload admitted only once that locked configuration has been verified
EnforcementIDE on every transactionBudgets enforced at the source: bandwidth regulation, time-aware gates, bounded execution windows
ContinuityRuntime re-attestation (open problem)Runtime overrun detection that leads to a defined safe state (open problem)

The first composition rule carries over directly. A budget without verified configuration is a budget nobody can check; a verified configuration without enforcement is a measurement, not a guarantee; and a deadline monitor without either is an alarm. The second rule does not carry over, and that is the subject of the next section.

4. Why time is harder: it adds up

Security fails at the weakest link. Timing fails at the sum. The end-to-end latency of a sensor-to-actuator path is bounded only if every hop on it is bounded, and the bound is the composition of all of them. A strong hop does not compensate for a weak one, and one unbounded hop makes the whole path unbounded.

That has two consequences that a trust chain does not face.

  • Budgets must be enforced at the source. In a trust chain, a compromised component damages its own trustworthiness. In a time chain, an unpoliced aggressor consumes shared cache, bandwidth or accelerator time and breaks the bounds of components it never touches. A budget that the aggressor is trusted to respect is not a budget.
  • Hop boundaries must compose. If each hop's output appears whenever that hop happens to finish, every scheduling change upstream moves the timing of everything downstream, and end-to-end analysis has to be redone. The Logical Execution Time (LET) model, which originated with time-triggered programming and is now used in automotive software, fixes this by making each task read its inputs at the start of a fixed window and publish its outputs at the end, whatever happens inside. Communication then occurs only at fixed points, which gives deterministic timing and data flow and lets tasks compose without re-analysis. Network hops can be modelled the same way, as windows sized to the worst-case transmission time.

LET has a cost: outputs appear at the end of the window even when the work finished early, which lengthens end-to-end latency, and current research reduces that pessimism using knowledge of the schedule. Its value is that it is the timing equivalent of a well-defined trust boundary. An overrun is detectable at exactly one point, the window end.

5. Where the chain of time breaks today

Following a sensor sample through a consolidated platform, hop by hop, shows where timing is enforced, where it is only detected, and where nothing bounds it by design. The last column gives the nearest layer in the MCIB interference-channel taxonomy: the hop says where time is lost, the layer says why.

AcceleratorMost accelerators run work sequentially, without preemption or concurrent execution; research frameworks such as PAAM schedule requests by chain priorityNot bounded by defaulthw.accel (proposed in MCIB spec v1.4)

Three observations follow.

  • Only the edges are enforced. The field network is the best-behaved hop. Inside the SoC, where the inference and the control loop actually meet, timing is detected at best.
  • Detection is often mistaken for enforcement. A deadline callback reports a miss after it has happened. It is the timing equivalent of an intrusion alarm: necessary, and no substitute for a lock.
  • The accelerator is the least-contracted hop and the most important one for Physical AI, because perception and vision-language-action inference run there.

Each loose hop has research that bounds it in isolation. What none of them has is a contract that carries across to the next hop.

6. The trust chain has gaps too

The trust row of the table in section 2 is not uniformly mature either, and the picture differs by domain.

Automotive sensors now have a standard path. The MIPI Camera Security Framework, released in 2024, uses DMTF SPDM to authenticate image sensors and the SerDes bridges that connect them to an ECU, and adds integrity protection and optional encryption of the image stream. It was motivated by UN R155, which lists manipulation of sensor data among in-vehicle vulnerabilities. A command-and-control companion specification followed in December 2025, and security IP implementing the framework was announced in 2026. I have not found evidence of production vehicles shipping it yet.

Robotics has no native equivalent that I could find. ROS 2 security, through SROS 2 and DDS-Security, authenticates and authorises software participants and encrypts topics. As a 2026 analysis points out, those guarantees apply once messages enter the protected stack; they do not establish whether the published data reflects the robot's physical state. Hardware attestation of robot nodes appears in research and in component-level authenticator chips, not in a robotics standard. The MIPI framework states that it can also apply to industrial uses of the same camera interface, so robot cameras have a route even though robotics did not create it.

The two dimensions meet at this point. A sample can be authentic and stale. It can be fresh and from a tampered sensor. A control loop needs both properties, and today they are checked, where they are checked at all, by unrelated mechanisms.

7. What would close it

All of the following are proposals.

Five building blocks

  • Declared timing contracts. Each workload and each hop declares its demand and its bound in machine-readable form: memory footprint, bandwidth envelope, burst profile, worst-case latency split into floor and tail. MCIB's specification already defines such a format as its Timing Manifest profile, with contracts derived from measurement and validated by replay, and per-device-class contracts for virtualised device paths.
  • Enforcement at the source. Every declared budget is backed by a mechanism that limits the aggressor, not by the victim's hope: bandwidth regulation and cache partitioning, time-aware gates, accelerator arbitration with priority and bounded preemption.
  • Composable boundaries. LET-style windows at hop boundaries, so that end-to-end latency is a sum of fixed windows that can be analysed in advance, rather than a property discovered by measurement.
  • Attest the lock. The configuration that bounds interference is locked at boot, then measured and reported the way firmware is. This reuses machinery that already exists: SPDM already defines measurement types for hardware configuration and firmware configuration as well as for code (DSP0274, section 7.10.1.1). It is integrity evidence that the intended configuration is in force. It is not, on its own, evidence that deadlines are met.
  • Runtime continuity. Overrun detection at window boundaries, tied to a defined reaction: degrade, fall back or reach a safe state.

8. Where MCIB fits

MCIB, the Mixed-Criticality Interference Benchmark, is the evidence side of the time chain. Its loop is profile → attribute → countermeasure, and each attributed outlier ends in a verdict: tune (configuration removes it), partition (a named isolation mechanism bounds it) or ceiling (a structural limit to design around). In the terms of this paper, attribution tells you which hop broke its contract and why, and the verdict tells you whether that hop's contract can be enforced at all.

Its method fits the third shared requirement in section 2, evidence that does not come from the system being judged: it measures the victim, toggles the aggressor and attributes the difference, using hardware counters as corroboration where the silicon exposes them.

Its current state is stated plainly in its repository. It has produced no measurements yet; its harness has been validated on a Raspberry Pi 4B under PREEMPT_RT; the specification, taxonomy and results schema are published; the first campaign is planned on Renesas R-Car V4H, and an accelerator time-sharing campaign is in outline. Its output is structured interference characterisation data that a qualified assessor may use as input to a safety argument. It is not qualified safety evidence.

9. Open problems

  • Continuity, in both chains. Trust is mostly verified at admission, and time is mostly verified at design. Neither has a standard way to keep checking during operation.
  • Accelerators. Without bounded preemption or arbitration on the accelerator, no contract above it can be enforced. The software can only measure the consequences.
  • Composition across the SoC and the network. TSN bounds the wire and LET bounds tasks; joining them through virtualised devices and middleware into one analysable path is not yet standard practice.
  • Formats. There is no agreed machine-readable form for a timing contract, or for reporting partitioning configuration as attestation evidence.
  • Freshness against completeness. Device and storage protocols are built so that nothing is lost. Control loops need the latest value, not every value. Contracts need a way to say which.

None of this promises that nothing will go wrong. It aims at something more useful: knowing where timing can go wrong, containing it, and holding evidence that does not come from the system being judged.
