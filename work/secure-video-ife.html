Case study · Platform security

Secure video streaming for in-flight entertainment

Widevine L1 DRM and aviation-qualified secure boot on NXP i.MX8, designed for certification from day one.

Linaro · delivery director and tech lead
Context

A 4K in-seat display that studios will trust

An aircraft in-seat display (ISD) streaming H.265 content at 60 fps to a 4K screen, backed by an in-cabin server infrastructure. Premium studio content requires Google Widevine L1, the hardware-backed tier of DRM, so the video path has to be protected by hardware all the way from decryption to the display.

The challenge

Certified firmware that still has to change

In aviation, certified resident firmware is part of a component’s part number (P/N). Changing it means a P/N change request and recertification. That puts two requirements in tension:

  • Keep the immutable, P/N-certified boot code as small as possible, while the rest of the boot chain stays updatable for security fixes over a ten-year product life.
  • Establish a hardware root of trust and a Trusted Execution Environment that satisfy Widevine L1 certification.

All of it had to fit the customer’s existing BSP boot and update flow rather than replace it.

My role

What I did, and what my team did

I did most of the security work myself: the security-by-design analysis and threat model, the OP-TEE integration, secure boot and secure provisioning, and the trusted application side, including integrating OEMCrypto through the platform abstraction layer. My team, under my lead, delivered the Linux-side integration: kernel patch porting and the secure-buffer GStreamer pipeline. As delivery director I also owned the plan, the customer relationship and the path to certification.

The approach

Secure by design, from the first day

  • Requirements first. A gap analysis of the existing BSP against Widevine L1 certification and the FAA/EASA Part 25 P/N qualification requirements.
  • Threat model. Threat agents and mitigations for the runtime streaming service and for device provisioning, which defined the security architecture.
  • Secure boot designed for certification. A customised i.MX8 HAB4 secure boot flow, using hardware-accelerated crypto, with a minimal immutable footprint and SBOM.
  • A key hierarchy that can survive a leak. Two tiers of image packaging and signing, with two tiers of boot authentication keys, so keys can be revoked without exposing device root keys.
  • A hardware-protected video path. OP-TEE with hardware-assisted memory protection, secure storage and cryptographic services, carrying decrypted content through secure buffers to the display.
  • Fit, not replace. Integrated with the customer’s existing boot and update scheme, keeping it maintainable and configurable at runtime.
Illustrative threat model

Assets, threats and mitigations

The method in brief: identify the assets and trust boundaries, map threats with STRIDE, then tie each mitigation to the certification constraints. The table is representative of that method, not the customer’s threat model.

AssetThreat (STRIDE)Mitigation
Boot images and firmwareTampering, spoofing: running unauthorised codeHAB4 secure boot chain anchored in a hardware root of trust
Image-signing keysInformation disclosure: a signing key leaksTwo tiers of image signing and boot-authentication keys, so keys can be revoked without exposing device root keys
Content keys and decrypted videoInformation disclosure: content theftOP-TEE with secure buffers and a hardware-protected video path to the display
Device secrets and credentialsSpoofing: device cloningSecure provisioning; secure storage and cryptographic services in the TEE

Results

Certified on plan

Widevine L1Certification passed, on plan
P/N qualificationSecure boot scheme qualified, on plan
EASACertified for installation on A320 aircraft
First in marketFirst commercial IFE product on NXP’s Linux Widevine L1 solution

Because compliance was designed in, the solution met the Widevine L1 and P/N qualification requirements from the start of development. The in-seat display and the in-cabin server infrastructure were successfully deployed.

What followed

Repeat business, earned on delivery

On the strength of this delivery, NXP engaged Linaro as a partner for its Linux Widevine L1 solution and referred a second, US-based IFE manufacturer. That customer awarded three successive projects, all of which I led:

  • Gap analysis, proof of concept and scope sizing to migrate NXP’s Widevine L1 stack from the deprecated OEMCrypto v15 to v19.6;
  • Production enablement of NXP’s Widevine L1 DRM Linux solution, through device qualification;
  • A content-distribution server on Qualcomm QCS8550: migration from legacy Qualcomm Linux Embedded (LE) to open-source Qualcomm Linux (meta-qcom), with SDUC storage and PCIe high-speed Ethernet (in progress in 2026).
